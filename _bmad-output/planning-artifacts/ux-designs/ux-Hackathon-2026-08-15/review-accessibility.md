# Accessibility review — Reconciliation Prototype

Scope: `DESIGN.md` and `EXPERIENCE.md`, reviewed against the stated desktop Electron prototype and WCAG AA commitment. Findings identify decisions that are absent or insufficiently specific; they do not expand product scope.

| Severity | Location | Finding | Concrete fix |
| --- | --- | --- | --- |
| High | EXPERIENCE.md:48, 75, 84, 88 | The results grid is required to work by keyboard and be programmatically discernible, but it has no keyboard interaction contract or semantic model. An implementer cannot tell how focus enters the grid, moves between cells/rows, reaches sorting/filtering/column controls, or how a virtualized grid exposes row and column context. | Specify either a semantic HTML table or an ARIA `grid` implementation. Define Tab entry/exit; arrow-key row/cell movement; Home/End and Page Up/Down behavior; Enter/Space selection and sort activation; the keyboard path to filters and column controls; and announced row/column counts, selected state, sort direction, and current filtered-result count. Preserve native table semantics where possible. |
| Medium | EXPERIENCE.md:50, 75, 85 | “Maintain logical focus” does not decide what happens when a keyboard user selects a row and the persistent detail panel updates. Automatically moving focus can make scanning difficult; leaving it in the grid can hide new evidence from assistive technology. The close/collapse return target is also undefined. | Keep focus on the selected grid row after ordinary selection and expose an explicit keyboard-accessible “Open inspector” control that moves focus to the detail-panel heading. On inspector close/collapse, restore focus to its invoker (or the selected row if that invoker is unavailable). Announce selection/detail updates succinctly without moving focus. |
| Medium | EXPERIENCE.md:64–70, 78, 88 | Run completion, result/filter changes, comment saves, and report saves/failures require visible feedback, but there is no requirement for assistive-technology announcement or error-message association. A screen-reader user may not know whether the operation completed or failed. | Add a dedicated status region for non-blocking progress and success updates, plus an assertive error region for failures. Programmatically associate each failure with its relevant control and retry action. Include the saved destination in the report-success announcement and preserve comment text and focus on failed comment saves. |
| Medium | EXPERIENCE.md:44, 63, 88 | The as-of-date field is only required to be valid before the Run button is enabled. The invalid/missing-date path, accessible label, validation text, and focus treatment are not defined. Disabled-only validation can leave keyboard and screen-reader users without an explanation. | Require a visible, programmatically associated label and validation message. If Run is attempted without a valid date, move focus to the date field (or an error summary linked to it), identify the required format/value in text, and expose the error with `aria-describedby`/equivalent native semantics. |
| Medium | EXPERIENCE.md:54, 79, 84–85 | “Reviewable draft context” for broker email has no declared interaction type. If it becomes a dialog, focus containment and return behavior are required; if it is a non-modal panel, its relationship to the invoking record must remain clear. | Choose and document one model. Prefer an adjacent/non-modal preview panel for this workflow; give it a labelled heading containing the broker/trade context and a keyboard return route. If a modal dialog is retained, set initial focus deliberately, trap focus, support Escape only where safe, and return focus to the preview invoker on close. |
| Low | DESIGN.md:8–21, 70; EXPERIENCE.md:87 | WCAG AA is promised, yet every color token and contrast value is still an assumption. The contracts do not state the minimum contrast thresholds for normal text, non-text controls/borders, or focus indicators in both themes. | Before implementation, assign tested light and dark token values and record minimums: 4.5:1 for normal text (3:1 only for qualifying large text), and 3:1 against adjacent colors for controls, essential grid boundaries, and focus indicators. Test status icon/text combinations independently of their colored background. |
| Low | DESIGN.md:55, 92; EXPERIENCE.md:71, 89, 95 | Light/dark and reduced-motion support are specified, but there is no decision for operating-system high-contrast/forced-colors mode. System-theme following alone can leave status, selected-row, focus, and error distinctions unusable for a user who enables high contrast. | Add a platform rule: honor `forced-colors`/OS high-contrast settings, avoid hard-coded color-only affordances in that mode, and verify selected rows, focus, status text/icons, validation, and warning/error differentiation using system colors. |
| Low | EXPERIENCE.md:93 | The collapsed inspector is called “accessible,” but keyboard invocation, current state, and focus behavior at narrow widths are unspecified. | Define the inspector toggle as a labelled button with exposed expanded/collapsed state; keep the selected-record context in its accessible name; and apply the focus-return rule from the detail-panel contract when it collapses or reopens. |

## Review outcome

The documents establish a sound accessibility floor—keyboard support, visible focus, non-color status treatment, AA intent, and reduced motion—but need the grid, focus, announcement, validation, and preview contracts above before implementation can reliably meet that floor.
